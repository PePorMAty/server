# Материальный баланс

Расчёт материального баланса одного преобразования графа моделью с
веб-поиском: сколько целевого продукта получается из исходного и какие
потоки идут рядом. Код — `routes/material-balance/`.

## Единица расчёта

Одно преобразование: **исходный продукт → преобразование → целевой
продукт**. Промпт рассчитан на цепочку продуктов «А → Б → В» без развилок, и
одно преобразование — её частный случай (А → Б). Остальные входы и выходы
преобразования (метанол у «Получения МТБЭ») уходят в контекст графа, и модель
считает их как дополнительные потоки.

Цепочки из нескольких преобразований собирает клиент из посчитанных шагов:
массы пропорциональны, и коэффициенты шагов перемножаются с тем же
допущением, что и в промпте, — весь промежуточный продукт идёт дальше.

## Базис

Модель **всегда считает на 1 т исходного продукта**. Пересчёт на любое
количество и единицу, а также обратный вопрос («сколько сырья на 50 т
продукта») делает клиент — пропорцией. Так один расчёт годится для любого
базиса, и готовое из базы подходит всем.

## Маршруты

| Метод и путь | Что делает |
|---|---|
| `GET /api/graphs/material-balance/prompt` | Промпт по умолчанию: `system`, `template`, `placeholders`, `basisKg` |
| `POST /api/graphs/material-balance/lookup` | Готовые расчёты пары в базе: `exact` и `similar` |
| `POST /api/graphs/material-balance` | Запустить расчёт или сразу отдать готовый |
| `GET /api/graphs/material-balance/jobs/:id` | Ход расчёта: `running` / `done` (с `result`) / `failed` (с `error`) |
| `GET /api/graphs/material-balance/:id` | Расчёт из базы по номеру |

### Запуск

```json
{
  "transformation": { "id": "t1", "name": "Получение МТБЭ", "description": "…" },
  "basis":  { "id": "n1", "name": "Изобутилен", "description": "…" },
  "target": { "id": "n2", "name": "МТБЭ" },
  "inputs":  [{ "id": "n1", "name": "Изобутилен" }, { "id": "n3", "name": "Метанол" }],
  "outputs": [{ "id": "n2", "name": "МТБЭ" }],
  "knownData": "Конверсия 96% по данным завода",
  "system": "…", "template": "…",
  "provider": "qwen", "model": "qwen3.7-plus",
  "force": false
}
```

Ответ — либо готовый расчёт из базы (`fromCache: true, result`), либо номер
задачи (`jobId`). Модель с веб-поиском отвечает минуты, поэтому расчёт идёт в
фоне, а клиент спрашивает `jobs/:id`. Готовый ответ пишется в базу, даже если
клиент ушёл: следующий такой же запрос получит его сразу.

Тот же запрос, пока первый ещё считается, получает ту же задачу — второй
щелчок «Рассчитать» к модели второй раз не идёт. Задачи живут в памяти
процесса: после перезапуска сервера недосчитанное пропадает (`jobs/:id` → 404
с объяснением), а досчитанное уже лежит в базе.

### Что берётся из базы

Ключ — **исходный продукт + целевой продукт + технология**:

- продукты — по справочнику, как сохранённые веб-источники (`productKey`):
  расчёт для «Кумола» найдётся и у «Изопропилбензола»;
- технология — по основам слов (`techKey`): «Получение МТБЭ» = «получения
  МТБЭ», «C4» латиницей = «С4» кириллицей.

`exact` — та же технология и обычный запрос: его `POST` отдаёт сразу, без
модели. `similar` — та же пара по другой технологии или со своими условиями,
по одному на технологию; их клиент только предлагает.

Не берутся из базы:

- расчёты «Недостаточно данных» — в следующий раз модель может найти больше;
- «Некорректный выбор» и «Не задан корректный базис» — это ошибка запроса, а
  не знание о технологии;
- запрос со своими данными (`knownData`) или правленым промптом — это просьба
  посчитать именно так; `force: true` — «Пересчитать».

Когда у преобразований появятся свои идентификаторы, ключом станут они.

## Промпт

Текст — заказчика (`utils/prompt.js`). От себя добавлен раздел ответа
**«Коэффициенты переходов»**: выход или расход стадии в «Расчёте по
переходам» есть лишь текстом, а клиенту он нужен числом — «выход 82%» на узле.

Плейсхолдеры заполняет сервер:

- `<<<SELECTED_PRODUCTS>>>` — P1 (исходный) и P2 (целевой) с описаниями;
- `<<<GRAPH_CONTEXT>>>` — активный маршрут, все входы и выходы преобразования
  T1 и оговорка, что других стадий в участке нет;
- `<<<BASIS>>>` — «P1 «…»: 1 т (1000 кг)»;
- `<<<KNOWN_DATA>>>` — свои данные или «Нет.»;
- `<<<SERVER_SOURCE_CHECKS>>>` — «Не передавались»: источники сервер не
  скачивает и не проверяет, берётся то, что пришло в ответе модели (как при
  построении шага). Поэтому у источников всегда `server_status: not_checked`.

ID узлов графа модели не уходят: они длинные, и модель их коверкает. Узлы
называются P1, P2, P3… и T1, а сопоставление (`refs`: обозначение, название,
роль) хранится с расчётом — по ролям клиент применит расчёт и на другом графе.

## Разбор ответа

`utils/parse.js` берёт из Markdown:

- статус: `calculated`, `partial`, `insufficient`, `invalid_selection`,
  `invalid_basis` (строка шаблона, переписанная целиком, — `unknown`);
- массы продуктов на 1 т исходного: число или диапазон, «≈» — оценка, «Нет
  данных» — пусто, тонны в колонке кг переводятся;
- коэффициенты переходов, внешние потоки «Общего баланса участка» и итоги;
- источники `[S1]…` со ссылками;
- разделы целиком для показа: расчёт по переходам, общий баланс, примечания.

Ответ без распознанного статуса — не по шаблону: задача завершается ошибкой
с началом ответа, в базу он не пишется.

## Хранение

SQLite `data/material-balance.sqlite` (путь — `MATERIAL_BALANCE_DB`), таблица
`balances`: ключи, подписи, статус, ответ целиком, разбор, обозначения узлов,
свои данные, отметка о правке промпта, модель, время расчёта.
