# Материальный баланс

Расчёт материального баланса преобразования графа моделью с веб-поиском:
сколько каждого продукта получается из сырья и какие потоки идут рядом. Код
— `routes/material-balance/`.

## Единица расчёта

**Преобразование целиком**: всё его сырьё и выбранные продукты — А + Б → В +
Г. Так требует промпт заказчика: «Единица расчёта — преобразование целиком,
со всеми входами и выходами… Не разбивай А + Б → В + Г на независимые
расчёты каждой пары продуктов». Запрос к модели один, а каждый продукт она
считает отдельно — своей строкой результатов, своими коэффициентами и
расчётом. Клиент по щелчку на продукт показывает расчёт именно этого
продукта: «А + Б → В».

Продукты, которые человек не выбрал, уходят в контекст как «не выбраны»:
модель знает о них, но отдельно их массы не считает.

Цепочки из нескольких преобразований промпт тоже умеет; клиент пока
посылает одно преобразование.

## Количество

Человек задаёт количество **опорного сырья** — одного из входов, в кг, т или
тыс. т (модели тысячи тонн уходят тоннами: промпт знает «кг» и «т»). Модель
считает на него и сама находит, сколько нужно остального сырья («Количества
остальных входов не заданы: рассчитай, сколько их требуется…»). Её ответ —
рецепт: массы всего сырья и всех продуктов на это количество.

Другие количества — любого сырья — клиент пересчитывает пропорцией, с
лимитирующим сырьём и остатками, без нового запроса. Поэтому количество не
входит в ключ готового расчёта: расчёт на 5 т пропилена годится и для 2 т,
и для запроса «от 300 кг аммиака».

Количество, с которым считали, хранится с расчётом (`basisAmount`): разделы
ответа модели клиент показывает как есть, с пометкой «числа в них на 5 т
«Пропилен»».

## Маршруты

| Метод и путь | Что делает |
|---|---|
| `GET /api/graphs/material-balance/prompt` | Промпт по умолчанию: `system`, `template`, `placeholders`, `units` |
| `POST /api/graphs/material-balance/lookup` | Готовые расчёты в базе: `exact` и `similar` |
| `POST /api/graphs/material-balance` | Запустить расчёт или сразу отдать готовый |
| `GET /api/graphs/material-balance/jobs/:id` | Ход расчёта: `running` / `done` (с `result`) / `failed` (с `error`) / `cancelled` |
| `POST /api/graphs/material-balance/jobs/:id/cancel` | Отменить расчёт: запрос к модели обрывается, в базу ничего не пишется |
| `GET /api/graphs/material-balance/:id` | Расчёт из базы по номеру |

### Запуск

```json
{
  "transformation": { "id": "t", "name": "Окислительный аммонолиз пропилена", "description": "…" },
  "inputs":  [{ "id": "pr", "name": "Пропилен" }, { "id": "nh3", "name": "Аммиак" }],
  "outputs": [{ "id": "acn", "name": "Акрилонитрил" }, { "id": "hcn", "name": "Синильная кислота" }, { "id": "act", "name": "Ацетонитрил" }],
  "targets": ["acn", "hcn", "act"],
  "basis": { "id": "pr", "amount": 5, "unit": "т" },
  "knownData": "Выход акрилонитрила 80% по данным завода",
  "system": "…", "template": "…",
  "provider": "qwen", "model": "qwen3.7-plus",
  "force": false
}
```

- `inputs` — всё сырьё преобразования, `outputs` — все его продукты;
  продукт, переданный и там и там, — сырьё;
- `targets` — id продуктов, для которых считать; нет — все;
- `basis` — опорное сырьё (id из `inputs`), количество и единица: «кг», «т»
  или «тыс. т». Неверное количество, единица или id — 400 сразу, без
  модели.

`lookup` принимает `{ transformation, inputs, targets }` — названиями или
узлами.

**Прежний вид** — пара `basis` + `target` узлами (клиент прежней версии):
это тот же расчёт с одним продуктом на 1 т сырья. Сервер принимает его как
раньше, и `lookup` пары (`{ transformation, basis, target }`) тоже работает.

Ответ — либо готовый расчёт из базы (`fromCache: true, result, nodeIds`),
либо номер задачи (`jobId`). `nodeIds` — какие узлы этого запроса стоят за
обозначениями готового расчёта: он мог быть сделан на другом графе, и узлы
сопоставлены по справочнику (`productKey`) — сырьё среди сырья, продукты
среди продуктов. Свежий расчёт несёт id узлов в `refs`.

Модель с веб-поиском отвечает минуты, поэтому расчёт идёт в фоне, а клиент
спрашивает `jobs/:id`. Готовый ответ пишется в базу, даже если клиент ушёл:
следующий такой же запрос получит его сразу.

Тот же запрос, пока первый ещё считается, получает ту же задачу — второй
щелчок «Рассчитать» к модели второй раз не идёт. В подписи запроса — id
узлов: свежий расчёт несёт их в `refs`, и чужой граф с теми же названиями их
получить не должен. Задачи живут в памяти процесса: после перезапуска
сервера недосчитанное пропадает (`jobs/:id` → 404 с объяснением), а
досчитанное уже лежит в базе.

### Отмена

«Отменить расчёт» на клиенте — `POST jobs/:id/cancel`. Задача получает статус
`cancelled`, а запрос к модели обрывается (`AbortController` → `signal` в
`callOpenAIResponsesRaw`, у OpenAI и у DashScope одинаково): сервер больше не
ждёт ответа, и в базу ничего не пишется, даже если ответ успел прийти.
Закончившуюся задачу отмена не трогает. Задача общая для одинаковых
запросов, поэтому отмена останавливает её и для второй вкладки — там опрос
получит `cancelled`. Тот же запрос после отмены — новая задача.

### Что берётся из базы

Ключ — **технология + набор сырья + набор продуктов**:

- продукты — по справочнику, как сохранённые веб-источники (`productKey`):
  расчёт для «Кумола» найдётся и у «Изопропилбензола»; порядок не важен;
- технология — по основам слов (`techKey`): «Получение МТБЭ» = «получения
  МТБЭ», «C4» латиницей = «С4» кириллицей.

`exact` — расчёт преобразования целиком (не прежней пары) той же
технологии, с тем же сырьём и теми же продуктами, обычный запрос: его `POST`
отдаёт сразу, без модели. `similar` — расчёты, где посчитаны все нужные
продукты (и, может быть, ещё какие-то) хотя бы с одним общим сырьём: другая
технология, другое сырьё, больше продуктов, свои данные, прежние расчёты
пар; по одному на вариант, свежие первыми. Их клиент только предлагает.

Не берутся из базы:

- расчёты «Недостаточно данных» — в следующий раз модель может найти больше;
- «Некорректный выбор» и «Не задан корректный базис» — это ошибка запроса, а
  не знание о технологии;
- запрос со своими данными (`knownData`) или правленым промптом — это просьба
  посчитать именно так; `force: true` — «Рассчитать заново».

Когда у преобразований появятся свои идентификаторы, ключом станут они.

## Промпт

Текст — заказчика, дословно (`utils/prompt.js`, из
`material_balance_prompt_2.md`). Наших добавок в нём больше нет: прежние —
раздел «Коэффициенты переходов», пять источников, «Оформление ответа» — в
новый текст не перенесены. Выход клиент считает по массам из «Результатов
по продуктам», а LaTeX и служебные имена дочищает сам.

Плейсхолдеры заполняет сервер:

- `<<<SELECTED_PRODUCTS>>>` — всё сырьё и выбранные продукты с описаниями:
  «- P1 — Пропилен (вход T1, опорный). …», «- P2 — Акрилонитрил (выход
  T1).»;
- `<<<GRAPH_CONTEXT>>>` — преобразование T1 с описанием, активный маршрут
  «P1 + P3 → T1 → P2 + P4», все входы и выходы на графе (какие выбраны,
  какие нет) и оговорка, что других стадий в участке нет;
- `<<<BASIS>>>` — «P1 «Пропилен»: 5 т (5000 кг).» и, если сырья несколько,
  «Количества остальных входов (P3 «Аммиак») не заданы: рассчитай, сколько
  их требуется…»;
- `<<<KNOWN_DATA>>>` — свои данные или «Нет.»;
- `<<<SERVER_SOURCE_CHECKS>>>` — «[] — серверная загрузка источников не
  выполнялась.»: пустой список, как в примечании заказчика к первому
  запросу. Источники сервер пока не скачивает и не проверяет, поэтому у них
  `server_status: not_checked`. Загрузка по URL с сохранением и повторный
  запрос к модели при `failed` — следующий шаг.

ID узлов графа модели не уходят: они длинные, и модель их коверкает. Узлы
называются P1, P2… и T1; сопоставление (`refs`: обозначение, id узла,
название, роль) хранится с расчётом. Роли: `basis` — опорное сырьё (P1),
`target` — продукты расчёта (первый — P2), `input` — прочее сырьё, `output`
— невыбранные выходы, `transformation` — T1. P1 и P2 — как у прежнего
расчёта пары, поэтому клиенты обеих версий читают записи друг друга.

## Разбор ответа

`utils/parse.js` берёт из Markdown:

- статус: `calculated`, `partial`, `insufficient`, `invalid_selection`,
  `invalid_basis` (строка шаблона, переписанная целиком, — `unknown`);
- «Схему участка» (`chain`), базис, характер результата;
- массы из «Результатов по продуктам» на количество, с которым считали:
  число или диапазон, «≈» — оценка, «Нет данных» — пусто, тонны в колонке кг
  переводятся;
- «Расчёт по преобразованиям» по полям (`steps`: заголовок «А + Б → В + Г»
  и поля «Входные потоки», «Коэффициенты», «Расчёт», «Проверка стадии»… с
  вложенными пунктами) — из них клиент собирает расчёт одного продукта;
- внешние потоки «Общего баланса участка» и итоги;
- источники `[S1]…` со ссылками и «Использован для»;
- разделы целиком для показа: расчёт по преобразованиям, общий баланс,
  примечания.

Ответы прежнего промпта тоже читаются: «Цепочка», «Расчёт по переходам»,
таблица «Коэффициенты переходов».

Ответ без распознанного статуса — не по шаблону: задача завершается ошибкой
с началом ответа, в базу он не пишется.

## Хранение

SQLite `data/material-balance.sqlite` (путь — `MATERIAL_BALANCE_DB`), таблица
`balances`: ключи, подписи, вид (`kind`: `transformation` или `pair`), набор
сырья и продуктов (ключи и названия), **название** (`title`: «Окислительный
аммонолиз пропилена → Акрилонитрил, Синильная кислота, Ацетонитрил» —
продукты, для которых посчитано), количество опорного сырья, статус, ответ
целиком, разбор, обозначения узлов, свои данные, отметка о правке промпта,
модель, время расчёта.

`basis_key` и `target_key` — опорное сырьё и первый продукт: ключ прежнего
поиска пары.

Новые колонки сервер добавляет сам при открытии старой базы, а прежние
расчёты пар переносит в них: сырьё и продукт — из обозначений, название
«Преобразование → Продукт», количество 1 т. Так их находит и новый поиск —
среди похожих.

Колонка `direction` осталась от недолгой версии с расчётами «вверх» (на 1 т
продукта). Все расчёты пишутся как `down`, а строки `up`, если успели
появиться, в ответы не идут — их числа посчитаны на другой базис.
