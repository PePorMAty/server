# План: данные — в PostgreSQL

Черновик для обсуждения с владельцем (2026-10-29). Цель — одна серверная
база для графов, источников и расчётов, на которой потом встанут групповая
работа, пользователи и доступ ИИ к данным (GraphRAG). Клиент на каждом этапе
работает как раньше: меняется хранилище за API, а не API.

## Что есть сейчас

| Данные | Где | Кто пишет | Объём (прод, 2026-10-29) |
|---|---|---|---|
| Графы библиотеки | `data/saved-graphs/<id>.json` (meta, graph, state) | `routes/graph-files` | 17 графов, самый большой — 687 узлов |
| Закладки, история, расчёты баланса графа, идентификаторы продуктов | `data/{bookmarks,history,material-balances,product-ids}/<id>.json` — сайдкары | `routes/graph-files` | по файлу на граф |
| Ссылки «Поделиться» | `data/shared-graphs/` | `routes/share` | |
| Правленый шаблон промпта | `data/prompt-layout.json` | `routes/graph-files` | 1 файл |
| База источников: документы, разделы, вещества разделов | `data/local-sources/sources.sqlite` + PDF в `files/` | `routes/local-sources` | 5 документов, ~180 разделов |
| Расчёты баланса (общие для всех графов), копии веб-страниц | `data/material-balance.sqlite` | `routes/material-balance` | ~70 расчётов |
| Реестр ГИСП, ОКПД2 | `data/gisp.sqlite` | `scripts/import-gisp.js` (только чтение сервером) | справочник |
| Старые таблицы `graphs/nodes/edges` | PostgreSQL (Sequelize, первый коммит) | никто | пусто; клиент их не читает |

Postgres на сервере уже есть и подключён (`/api/health` → `database:
connected`), драйвер `pg` в зависимостях.

**Что мешает сейчас.** Файл графа перезаписывается целиком, без версии:
двое правят один граф — побеждает последний, правка первого пропадает
молча. Связать графы между собой (тот же продукт в разных графах) и искать по
ним можно только перебором файлов. Резервная копия — это копия папки
`data/` в «тихий» момент.

## Принципы перехода

1. **API не меняется.** Те же адреса и ответы; клиент можно не трогать (кроме
   конфликта версий — этап 1, необязательное поле).
2. **По одному хранилищу за раз**, за переключателем в `.env`
   (`GRAPH_STORE=files|pg`, `SOURCES_STORE=…`). Хранилище — модуль с тем же
   набором функций, что сейчас `routes/graph-files/utils/store.js`; две
   реализации, тесты гоняются на обеих.
3. **Перенос — скриптом, повторяемым и с пробным прогоном** (`--dry`: что
   перенесётся, сколько, где расхождения). Файлы и SQLite после переноса
   не удаляются, пока владелец не подтвердит; есть обратная выгрузка в файлы
   — откат за минуты.
4. **Простой SQL, без ORM.** Код хранилищ уже на SQL (SQLite) — переносится
   почти построчно на `pg`. Миграции — файлы `db/migrations/NNN_*.sql` и
   маленький запускатель (`npm run db:migrate`), номер применённой — в
   таблице `schema_migrations`.
5. **Отдельная схема `app`**: старая таблица `graphs` (Sequelize) не мешает;
   её и `nodes/edges` удаляем отдельным шагом, когда убедимся, что никто не
   читает (`/api/graphs`, `/api/stats` — только они).

## Схема (набросок)

```sql
CREATE SCHEMA app;

-- Заготовка под пользователей: пока одна общая область, created_by пусто.
CREATE TABLE app.workspaces (id uuid PRIMARY KEY, name text NOT NULL, created_at timestamptz NOT NULL DEFAULT now());
CREATE TABLE app.users (id uuid PRIMARY KEY, email text UNIQUE, name text, created_at timestamptz NOT NULL DEFAULT now());
CREATE TABLE app.memberships (workspace_id uuid REFERENCES app.workspaces, user_id uuid REFERENCES app.users,
  role text NOT NULL DEFAULT 'editor', PRIMARY KEY (workspace_id, user_id));

-- Граф — документом (jsonb), как сейчас файл: клиенту отдаём то же самое.
CREATE TABLE app.graphs (
  id           text PRIMARY KEY,          -- прежнее имя файла: старые ссылки живут
  workspace_id uuid REFERENCES app.workspaces,
  name         text NOT NULL,
  content      jsonb NOT NULL,            -- { graph: {nodes, edges}, state }
  meta         jsonb NOT NULL DEFAULT '{}',
  node_count   int NOT NULL DEFAULT 0,
  version      int NOT NULL DEFAULT 1,    -- растёт с каждым сохранением
  created_by   uuid REFERENCES app.users,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now(),
  deleted_at   timestamptz                -- удаление — мягкое, восстановимо
);
-- Прежние сохранения: откатить чужую правку, посмотреть, что было.
CREATE TABLE app.graph_revisions (graph_id text REFERENCES app.graphs, version int,
  content jsonb NOT NULL, saved_by uuid, saved_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (graph_id, version));

-- Сайдкары — таблицами с ключом (граф, узел).
CREATE TABLE app.graph_bookmarks   (graph_id text, node_id text, label text, kind text, note text, updated_at timestamptz, PRIMARY KEY (graph_id, node_id));
CREATE TABLE app.graph_history     (graph_id text, seq bigserial, entry jsonb NOT NULL, at timestamptz, PRIMARY KEY (graph_id, seq));
CREATE TABLE app.graph_balances    (graph_id text, node_id text, calcs jsonb NOT NULL, updated_at timestamptz, PRIMARY KEY (graph_id, node_id));
CREATE TABLE app.graph_product_ids (graph_id text, node_id text, data jsonb NOT NULL, updated_at timestamptz, PRIMARY KEY (graph_id, node_id));
CREATE TABLE app.shares   (id text PRIMARY KEY, graph jsonb NOT NULL, created_at timestamptz NOT NULL DEFAULT now());
CREATE TABLE app.settings (key text PRIMARY KEY, value jsonb NOT NULL, updated_at timestamptz);

-- База источников — те же таблицы, что в SQLite; PDF остаются файлами на диске.
CREATE TABLE app.documents (...);          -- как в local-sources/utils/store.js
CREATE TABLE app.sections (...);
CREATE TABLE app.section_products (...);   -- ключ вещества → раздел, роль, направление
-- Расчёты баланса и копии веб-страниц — как в material-balance/utils/store.js.
CREATE TABLE app.balances (...);
CREATE TABLE app.web_documents (...);
```

Почему граф — документом, а не таблицами узлов и связей: клиент и так
сохраняет граф целиком, а 687 узлов — это сотни килобайт, jsonb с ними
справляется. Узлы и связи отдельными строками понадобятся для поиска по всем
графам — это этап 4, и там они будут **производными** (пересчитываются при
сохранении), а не вторым местом правды.

## Этапы

### Этап 0. Подготовка (полдня, делает владелец с моей инструкцией)
- Версия Postgres (`psql --version`), есть ли пакет pgvector для неё
  (`apt install postgresql-<версия>-pgvector`) — понадобится на этапе 4.
- Отдельная база и пользователь для приложения; переменные в `.env`.
- **Резервные копии**: `pg_dump` по cron раз в сутки + хранить 14 дней; и
  копия `data/` в то же время. Проверка восстановления — один раз руками.
- Заодно: на проде `NODE_ENV=development` (видно в `/api/health`) — в pm2
  поставить `production`. Проверю заранее, что это ничего не меняет, кроме
  синхронизации старых таблиц Sequelize при запуске.

### Этап 1. Графы и всё, что рядом (2–3 дня работы)
- `db/migrations/001_graphs.sql`, хранилище `graph-files` на `pg`.
- Скрипт `scripts/migrate-graphs-to-pg.js [--dry]`: файлы → таблицы, с
  отчётом (сколько графов, узлов, закладок; что не сошлось). Обратный —
  `scripts/export-graphs-from-pg.js`.
- **Конфликт правок.** Сохранение несёт версию, с которой граф открыли;
  сервер видит, что граф уже сохранил кто-то другой, — `409` и свежая версия.
  Клиент: «Граф изменили, пока вы работали: открыть их версию / сохранить
  свою копией». Старый клиент без версии — сохраняет как раньше.
- Проверка: тесты хранилища на обеих реализациях, e2e на домене, сравнение
  выгрузки «до/после» по всем 17 графам.

### Этап 2. Источники и балансы (2 дня)
- Перенос `sources.sqlite` и `material-balance.sqlite` в `app.*`; запросы
  почти те же. Полнотекстовый поиск разделов — `tsvector` по-русски (сейчас
  поиск по ключам названий; он остаётся, поиск по тексту — добавка).
- PDF и загрузки — на диске, как сейчас (путь в базе).
- ГИСП (`gisp.sqlite`) — пока не трогаем: справочник только для чтения,
  пересобирается скриптом целиком. Переносить, когда понадобится связать
  его с продуктами графов в одном запросе.

### Этап 3. Пользователи (когда решим открывать сервис)
- Таблицы уже есть с этапа 1; добавить вход: почта + пароль (argon2) или
  вход через Яндекс ID / VK ID, сессия в httpOnly-cookie.
- Рабочие области: у графа владелец и область, участники с ролями
  (смотрит / правит). Ссылки «Поделиться» — как сейчас, только чтение.
- 152-ФЗ: с появлением учётных записей нужен оператор персональных данных
  (лицо или организация в `terms.html`/`privacy.html`, см. клиентский
  `deploy/DEPLOY.md`), согласие при регистрации, хранение в РФ (сервер уже
  в РФ — проверить).

### Этап 4. Слой знаний и поиск — основа GraphRAG
- **Справочник продуктов** `app.products` (название, синонимы, ключи,
  ОКПД2/ТН ВЭД/CAS — часть уже определяется) и **преобразований**
  `app.transformations` (входы → выходы, источник: раздел ИТС или граф).
  Узлы графов ссылаются на продукты — тогда «тот же продукт в другом графе»
  и «переувязать узлы» — запрос, а не сравнение строк.
- Готовые рёбра уже есть: разбор разделов ИТС пишет «процесс: входы →
  выходы» и роли веществ. Это и есть граф знаний из документов — его
  достаточно перенести в эти таблицы.
- **Векторы** (pgvector): описания разделов и продуктов → эмбеддинги
  (DashScope text-embedding; на 180 разделов — копейки). Поиск: по словам +
  по смыслу + по связям графа (сосед, предок, альтернатива).

### Этап 5. Диалог с ИИ
- Поле «Задача для ИИ» на полотне: «добавь альтернативные способы производства
  бензола». Модель работает **инструментами**, а не прямым доступом к базе:
  найти продукт, источники продукта, построить шаг (наш конвейер: источники →
  обобщение → разбор со всеми страховками), показать превью, добавить в граф,
  связать с существующим узлом. Каждое изменение — через превью и
  подтверждение человека, как шаг сейчас.
- Проверка — сценарии e2e: «альтернативы бензола», «довести цепочку от фенола
  до волокна», на подставных ответах и живьём по просьбе.

## Риски и как их закрываем

| Риск | Что делаем |
|---|---|
| Потеря данных при переносе | Файлы не удаляются; пробный прогон; сравнение выгрузок; обратный скрипт |
| Память сервера (2 ГБ, рядом API и VPN) | Postgres с `shared_buffers=128MB` — около 150–250 МБ; данных мало |
| Два хранилища расходятся во время перехода | Переключатель — или файлы, или pg, двойной записи нет; перенос — в тихое время, библиотека маленькая (минуты) |
| Старые клиенты на сайте | API тот же; поле версии необязательное |
| Сбой базы | Ежедневный `pg_dump`, проверенное восстановление |

## Что нужно от владельца
1. Postgres на том же сервере? Версия, можно ли поставить pgvector.
2. Где хранить резервные копии (тот же диск — плохо: другой сервер или
   облако).
3. Согласие на порядок этапов и на «граф — документом jsonb».
4. Когда этап 1 готов — окно для переноса (в нём сайт работает, сохранение
   графов на минуты недоступно).
