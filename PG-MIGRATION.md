Черновик 2026-10-29, дополнен 2026-11-03 по ответам владельца. Цель — одна
серверная база для графов, источников и расчётов. На ней потом встанут
пользователи со своими и общими графами, совместная работа в реальном времени
и доступ ИИ к данным (GraphRAG). Клиент на каждом этапе работает как раньше:
меняется хранилище за API, а не API.

## Почему PostgreSQL, а не графовая база (Neo4j)

Вопрос владельца 2026-11-12: что лучше для графов, пользователей и
совместной правки онлайн — графовая база вроде Neo4j или PostgreSQL.

**Что нам нужно хранить и как с этим работают:**
- графы — по 10–700 узлов, открываются и сохраняются целиком;
- карточки узлов с длинными текстами, источники, расчёты баланса;
- пользователи, токены входа, права на графы, комментарии;
- журнал операций совместной правки, ревизии;
- позже — слой знаний (продукты, преобразования из ИТС) и векторы для
  GraphRAG.

Обход графа (цепочка вверх и вниз, окрестность фокуса) уже идёт в браузере
по загруженному графу. На сервере нужны «тот же продукт в других графах» и
поиск путей по слою знаний.

| | PostgreSQL | Neo4j |
|---|---|---|
| Уже есть | стоит (16.15), копии настроены, пользователь `graph_app` | ставить отдельно, вторая база в копиях |
| Память (на сервере 2 ГБ рядом с API и VPN) | ~150–250 МБ | JVM: на практике от 1–2 ГБ |
| Пользователи, токены, права, комментарии | сильная сторона: связи, ограничения, транзакции | хранить можно, но это не его задача |
| Граф целиком (jsonb) и журнал операций | jsonb + таблица операций | граф — узлами, документ целиком собирать запросом |
| Цепочки и пути | рекурсивные запросы (`WITH RECURSIVE`); при нужде — расширение Apache AGE: запросы openCypher прямо в PostgreSQL | сильная сторона: Cypher, поиск путей, алгоритмы графов |
| Векторы для GraphRAG | pgvector (пакет для 16 — в Ubuntu 24.04) | встроенный векторный индекс, готовые библиотеки GraphRAG |
| Полнотекстовый поиск по-русски | есть (tsvector) | слабее |
| Совместная правка онлайн | `LISTEN/NOTIFY` между процессами сервера | рассылки клиентам нет; поток изменений (CDC) — в платной версии |
| Лицензия и размещение | свободная, на нашем сервере в РФ | бесплатная Community без ролей доступа, кластеров и горячих копий; Enterprise — платная; облако Aura — за рубежом (152-ФЗ, оплата) |

**Вывод: PostgreSQL — единственное место правды.**

Совместную правку онлайн обеспечивает не база, а сервер с веб-сокетами
(этап 3в):
- правки идут по сокету и сразу рассылаются остальным из памяти комнаты;
- база лишь записывает журнал операций и снимки.

Поэтому здесь Neo4j ничего не даёт, а пользователи, права и комментарии —
задачи реляционной базы. Наши графы маленькие, и цепочки в них
PostgreSQL обходит мгновенно.

**Когда вернуться к графовой базе.** Если слой знаний вырастет до
межграфового поиска путей («все маршруты от нефти до ПАВ не длиннее 6
стадий»), шаги такие:
1. Попробовать Apache AGE (Cypher внутри того же PostgreSQL).
2. Если и его станет мало — Neo4j как копию только для чтения: её
   наполняют из PostgreSQL, а данные по-прежнему живут в PostgreSQL. Так
   же делают с поисковым индексом.

## Принципы перехода

1. **API не меняется.** Адреса и ответы остаются прежними, клиент можно не
   трогать. Исключение — конфликт версий на этапе 1, это необязательное поле.
2. **По одному хранилищу за раз**, за переключателем в `.env`
   (`GRAPH_STORE=files|pg`, `SOURCES_STORE=…`):
   - хранилище — модуль с тем же набором функций, что сейчас
     `routes/graph-files/utils/store.js`;
   - реализаций две, тесты гоняются на обеих.
3. **Перенос — скриптом, повторяемым и с пробным прогоном.**
   - `--dry` показывает, что перенесётся, сколько и где расхождения.
   - Файлы и SQLite после переноса не удаляются, пока владелец не подтвердит.
   - Есть обратная выгрузка в файлы, так что откат занимает минуты.
4. **Простой SQL, без ORM.**
   - Код хранилищ уже на SQL (SQLite) и переносится на `pg` почти построчно.
   - Миграции — файлы `db/migrations/NNN_*.sql` и маленький запускатель
     (`npm run db:migrate`).
   - Номер применённой миграции хранится в таблице `schema_migrations`.
5. **Отдельная схема `app`**, чтобы старая таблица `graphs` (Sequelize) не
   мешала.
   - Её и `nodes/edges` удаляем отдельным шагом, когда убедимся, что их никто
     не читает.
   - Сейчас их читают только `/api/graphs` и `/api/stats`.
6. **Место под пользователей готовим сразу, но не строим заранее.** На
   этапе 1 у записей появляется «кто сделал» (`created_by`, `updated_by` —
   пока пусто) и область (`workspace_id`). Каждая функция хранилища принимает
   `actor` — пока это «владелец». Тогда на этапе 3 добавятся проверка
   токена и права, а данные переносить заново не придётся. Таблицы прав,
   комментариев и операций создаются миграциями на своих этапах.

## Этапы

### Этап 0. Подготовка (полдня, делает владелец по инструкции)

**1. Что за Postgres.** Запустить из папки сервера:

```bash
node scripts/db-info.js
```

Скрипт подключится так же, как сервер, и покажет:
- версию;
- можно ли включить pgvector, и если нет — какой пакет поставить;
- может ли пользователь приложения создать схему `app`;
- память, размер базы и что в ней лежит.

Ничего не меняет. Если не подключится (`.env` не тот), то же руками:

```bash
sudo -u postgres psql -c "SELECT version();"
sudo -u postgres psql -c "SELECT name, default_version FROM pg_available_extensions WHERE name IN ('vector','pg_trgm');"
apt-cache policy postgresql-<версия>-pgvector      # есть ли пакет pgvector
pg_lsclusters                                       # какие кластеры и порты (Debian/Ubuntu)
docker ps | grep -i postgres                        # вдруг база в Docker
```

Подходит версия 13 и новее. pgvector нужен только к этапу 4: в Ubuntu 24.04 и
Debian 12 он есть в обычных пакетах, в остальных — в репозитории
apt.postgresql.org.

**2. Свой пользователь базы для приложения — не суперпользователь.**
*Сделано 03.11: сервер ходит в базу как `graph_app`.* Раньше он
подключался как `anton` (суперпользователь). Суперпользователь
Postgres может через `COPY … PROGRAM` выполнить любую команду на машине. Одна
ошибка в SQL, когда появятся пользователи, — и это уже доступ к серверу, а не
к базе. Поэтому:

```bash
cd ~/server
PASS=$(openssl rand -hex 24)          # пароль — случайный, руками не набираем
sudo -u postgres psql -d gpt_graphs -v ON_ERROR_STOP=1 -v pass="$PASS" <<'SQL'
CREATE ROLE graph_app LOGIN PASSWORD :'pass';
ALTER DATABASE gpt_graphs OWNER TO graph_app;
-- старые пустые таблицы Sequelize — тоже ему: сервер создаёт их при запуске
DO $$ DECLARE t text; BEGIN
  FOR t IN SELECT tablename FROM pg_tables WHERE schemaname = 'public' LOOP
    EXECUTE format('ALTER TABLE public.%I OWNER TO graph_app', t);
  END LOOP;
END $$;
SQL
cp .env .env.bak-$(date +%F)          # откат: вернуть этот файл и pm2 restart all
sed -i "s/^DB_USER=.*/DB_USER=graph_app/; s/^DB_PASSWORD=.*/DB_PASSWORD=$PASS/" .env
node scripts/db-info.js               # «пользователь «graph_app»», без «(суперпользователь)»
pm2 restart all
curl -s https://sorangptgraph.xyz/api/health   # database: connected
```

Проверено на временном PostgreSQL 16: `graph_app` создаёт схему `app`,
пишет в старые таблицы, суперпользователем не является.

- Владелец базы может создавать в ней схемы и таблицы — этого хватает для
  миграций.
- Расширения (`vector`, `pg_trgm`) один раз включает `anton` или `postgres`.
- `anton` остаётся для ручной работы.

**3. Резервные копии** — по `BACKUP.md`:
- ключ age, приватный репозиторий, ключ развёртывания, cron;
- один раз проверить восстановление.

Копии уже сейчас собирают `data/`, обе базы SQLite и PDF, и в них попадёт
дамп Postgres, когда в нём появятся данные.

**4. Заодно.** На проде `NODE_ENV=development` (видно в `/api/health`) — в
pm2 поставить `production`. Заранее проверю, что это ничего не меняет, кроме
синхронизации старых таблиц Sequelize при запуске.

### Этап 3а. Пользователи и вход по JWT (3–4 дня)

```sql
CREATE TABLE app.users (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email text NOT NULL,
  name text NOT NULL,
  password_hash text,                 -- argon2id; пусто — вход только через Яндекс ID / VK ID
  email_verified_at timestamptz,
  token_version int NOT NULL DEFAULT 0,  -- +1 = «выйти на всех устройствах»
  created_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz
);
CREATE UNIQUE INDEX ON app.users (lower(email));
CREATE TABLE app.refresh_tokens (
  id uuid PRIMARY KEY,
  user_id uuid NOT NULL REFERENCES app.users,
  family uuid NOT NULL,               -- цепочка обновлений одного входа
  token_hash bytea NOT NULL,          -- sha256; сам токен есть только у браузера
  expires_at timestamptz NOT NULL,
  used_at timestamptz, revoked_at timestamptz,
  user_agent text, created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE app.email_tokens (token_hash bytea PRIMARY KEY, user_id uuid NOT NULL,
  purpose text NOT NULL,              -- 'verify' | 'reset'
  expires_at timestamptz NOT NULL, used_at timestamptz);
-- Модель стоит денег: сколько запросов сделал пользователь, и предел в день.
CREATE TABLE app.model_usage (user_id uuid, day date, kind text, requests int NOT NULL DEFAULT 0,
  PRIMARY KEY (user_id, day, kind));
```

**Два токена.**
- **Access** — JWT на 15 минут: `sub` — id пользователя, `tv` —
  `token_version`.
  - Ролей в токене нет: права на граф меняются, их сервер смотрит в базе.
  - Клиент держит его в памяти, а не в `localStorage`, чтобы чужой скрипт на
    странице его не унёс.
  - Передаётся в заголовке `Authorization: Bearer`.
- **Refresh** — случайная строка на 30 дней.
  - Хранится в httpOnly-cookie (`Secure`, `SameSite=Strict`,
    `Path=/api/auth`), в базе — только её хэш.
  - При каждом обновлении выдаётся новая, старая помечается
    использованной.
  - Если кто-то предъявит уже использованную, значит её украли: отзывается
    вся цепочка, и нужно войти заново.

**Адреса:**
- `POST /api/auth/register`, `/login`, `/refresh`, `/logout`;
- `GET /api/auth/me`;
- подтверждение почты и сброс пароля — письмом. Почту отправлять через
  SMTP: Яндекс 360 или Unisender.

**Мелочи, которые потом дорого чинить:**
- подпись JWT — ключ из `.env` (`JWT_SECRET`, HS256), библиотека `jose`;
- пароли — `argon2id`;
- ограничение частоты на вход и регистрацию;
- одинаковый ответ «почта или пароль неверны», чтобы нельзя было проверить,
  зарегистрирован ли адрес.

**Запросы к модели.** Шаг, баланс, техописание, проверка «что из него делают»
— только после входа, с дневным пределом на пользователя (`model_usage`).
Сейчас эти адреса открыты всем.

**Старые клиенты.** Пока вход не обязателен (переключатель `AUTH_REQUIRED`),
всё работает анонимно, как сейчас. Включаем, когда клиент научится входить.

**Копия на GitHub Pages.** Она открывается с другого домена, и cookie входа
туда не попадёт. Вход будет работать только на sorangptgraph.xyz, а Pages
останется витриной без входа (или её выключаем — решает владелец).

**152-ФЗ.** С учётными записями нужно:
- оператор персональных данных — лицо или организация в
  `terms.html`/`privacy.html`, см. клиентский `deploy/DEPLOY.md`;
- согласие при регистрации;
- хранение в РФ (сервер уже в РФ — проверить);
- резервные копии с персональными данными — тоже в РФ (`BACKUP.md`, конец).

### Этап 3б. Свои и общие графы, права — как в Figma (3 дня)

```sql
CREATE TABLE app.workspace_members (workspace_id uuid REFERENCES app.workspaces, user_id uuid REFERENCES app.users,
  role text NOT NULL,                 -- 'admin' | 'member' | 'guest'
  PRIMARY KEY (workspace_id, user_id));
CREATE TABLE app.graph_access (graph_id text REFERENCES app.graphs, user_id uuid REFERENCES app.users,
  role text NOT NULL,                 -- 'owner' | 'editor' | 'commenter' | 'viewer'
  granted_by uuid, granted_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (graph_id, user_id));
CREATE TABLE app.invites (id uuid PRIMARY KEY, graph_id text, workspace_id uuid, email text NOT NULL,
  role text NOT NULL, invited_by uuid, created_at timestamptz NOT NULL DEFAULT now(), accepted_at timestamptz);
ALTER TABLE app.graphs ADD COLUMN owner_id uuid REFERENCES app.users,
  ADD COLUMN link_access text NOT NULL DEFAULT 'none',   -- 'none' | 'view' | 'comment' | 'edit'
  ADD COLUMN link_token text UNIQUE;
```

**Где живут графы:**
- **Мои графы** — личная область, создаётся при регистрации.
- **Команды** — общие области: участники видят графы команды.
- **Общая библиотека** — нынешние 17 графов. Видна всем, правят её
  администраторы. Чтобы поработать с её графом, остальные делают себе копию.

**Роли на графе:**
- *смотрит*;
- *комментирует*;
- *правит*;
- *владелец* — может делиться и удалять.

Итоговое право — наибольшее из трёх:
- роль в области;
- личный доступ к графу;
- доступ по ссылке.

**Ссылки.** «Поделиться» умеет:
- пригласить по почте — тот, у кого ещё нет учётной записи, получит доступ
  после регистрации;
- выдать ссылку с ролью: «все, у кого есть ссылка, могут смотреть /
  комментировать / править».

Нынешние снимки «Поделиться» остаются как есть — копия графа только для
чтения.

**Проверка прав — в одном месте.** Это middleware `canGraph(role)`, через
него проходит каждый запрос к графу и его сайдкарам. Тесты: «чужой граф — 404,
а не 403», то есть сам факт, что граф есть, не раскрываем.

### Этап 3в. Совместная работа: веб-сокеты, кто на графе, комментарии

Делаем по шагам, каждый полезен сам по себе.

**Шаг 1. Кто на графе и что делает (2 дня).**

Канал — один веб-сокет на граф:
- `wss://sorangptgraph.xyz/api/ws`, библиотека `ws` на том же Express;
- Socket.IO не нужен.

Вход:
- первое сообщение несёт access-токен. Не в адресе: адреса попадают в журналы
  nginx;
- сервер проверяет роль на графе;
- когда токен истекает, сервер просит новый, и клиент присылает его без
  переподключения;
- если права отозвали, сервер сообщает об этом и переводит клиента в
  просмотр.

Присутствие хранится в памяти сервера, по комнате на граф, а **не в базе**:
- кто открыл граф (аватар и цвет);
- курсор — до 10 раз в секунду;
- выделенные узлы;
- что делает: «правит карточку «Фенол»», «строит шаг вниз от «Фенол»»,
  «считает баланс «Алкилирование»».

Через 30 секунд после обрыва связи человек пропадает из списка.

В клиенте:
- аватары в шапке, курсоры и чужие выделения — отдельным слоем поверх
  полотна, а не в данных узлов: на графе из 687 узлов React Flow иначе
  перерисует каждый;
- «следовать за ним» — щелчок по аватару ведёт полотно за этим человеком.

**Мягкая блокировка долгих действий.** Шаг модель строит минутами. Если кто-то
уже строит шаг от «Фенола», другим видно «Анна строит шаг вниз от «Фенол»», а
при попытке построить тот же шаг — предупреждение. Запрета нет.

Сохранение пока прежнее, с версией этапа 1. Но остальные сразу видят «Анна
сохранила граф — обновить?» вместо 409 при своём сохранении.

**Шаг 2. Комментарии (3–4 дня).**

```sql
CREATE TABLE app.comment_threads (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  graph_id text NOT NULL REFERENCES app.graphs,
  anchor jsonb NOT NULL,              -- {"node": id} | {"edge": id} | {"x": .., "y": ..}
  anchor_label text,                  -- подпись узла на момент комментария
  created_by uuid NOT NULL, created_at timestamptz NOT NULL DEFAULT now(),
  resolved_at timestamptz, resolved_by uuid
);
CREATE TABLE app.comments (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  thread_id uuid NOT NULL REFERENCES app.comment_threads,
  author_id uuid NOT NULL, body text NOT NULL,
  mentions uuid[] NOT NULL DEFAULT '{}',   -- @упоминания → уведомление
  created_at timestamptz NOT NULL DEFAULT now(), edited_at timestamptz, deleted_at timestamptz

```

- Комментарии лежат **отдельно от графа**: не меняют его версию и не
  попадают в jsonb. Роль «комментирует» может их писать, а граф — нет.
- Ветка привязана к узлу, связи или точке полотна; её можно закрыть
  («решено»).
- Если узел удалили, ветка остаётся с пометкой «узел удалён» и прежней
  подписью — видно, о чём шла речь.
- Новые комментарии приходят остальным по тому же сокету, а загружаются
  обычным запросом.
- Письма об @упоминаниях — позже, сводкой.

**Шаг 3. Правка вдвоём в реальном времени (1–2 недели, главная работа — в
клиенте).**

```sql
CREATE TABLE app.graph_ops (graph_id text, seq bigint, user_id uuid, op jsonb NOT NULL,
  at timestamptz NOT NULL DEFAULT now(), PRIMARY KEY (graph_id, seq));
```

**Как устроено — как у Figma.** Порядок операций задаёт сервер, а при споре
о свойстве побеждает последняя запись.

1. Клиент шлёт операции, а не граф целиком: `node.add`, `node.set`
   (поле → значение), `node.move`, `node.remove`, `edge.add`,
   `edge.remove`, `step.apply`.
   - `step.apply` — весь шаг: узлы и связи из превью одной пачкой.
2. Клиент применяет их у себя сразу, не дожидаясь сервера.
3. Сервер:
   - проверяет роль;
   - применяет операции к графу в памяти комнаты по очереди и даёт каждой
     номер (`seq`);
   - рассылает всем, включая автора, — это подтверждение;
   - пишет операции в `graph_ops`.
4. Конфликты решаются по свойствам: двое двигают один узел — останется
   последнее положение. Двое правят разные поля карточки — сохранятся оба.
   Удаление сильнее правки: правка удалённого узла отклоняется, и автору об
   этом сообщают.
5. Шаг, построенный от узла, который тем временем удалили, сервер
   отклоняет. Клиент предлагает: «узел удалили, пока строился шаг — добавить
   шаг отдельно?».
6. Перетаскивание идёт «облегчённо», как курсор. Операцией становится только
   конечное положение.
7. Документ `graphs.content` пересобирается из операций раз в несколько
   секунд и когда последний человек уходит с графа. Ревизии
   (`graph_revisions`) — раз в час и перед «опасными» операциями (удаление
   многих узлов, откат). Операции старше 30 дней удаляются.
8. Связь оборвалась → клиент копит свои операции. После переподключения
   сервер досылает пропущенное с его последнего `seq`, и клиент переигрывает
   свои операции поверх.
9. Отмена (Ctrl+Z) — у каждого своя: клиент помнит обратные операции своих
   действий.
10. Журнал «кто что сделал» — это и есть `graph_ops`: «Анна добавила шаг вниз
    от «Фенол» (5 узлов), 14:02».
11. Старый клиент без сокета сохраняет как раньше. Сервер превращает это в
    операцию «граф целиком», и остальные её видят.

**Почему не Yjs (CRDT).** Yjs хорош там, где нужна работа без сервера и
слияние длинных текстов. У нас граф живёт в Redux и React Flow — пришлось бы
перенести его в документ Yjs, а это переписать клиент. ИИ-помощник этапа 5 и
наши проверки шага проще делать, когда граф держит сервер. Если понадобится
вместе писать длинный текст карточки, Yjs можно поставить только на него.

**Сервер для сокетов.**
- nginx:
  ```
  location /api/ws {
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 1h;
  }
  ```
- Комнаты живут в памяти, поэтому pm2 — **один процесс** сервера. Десяткам
  одновременных людей его хватит.
- Понадобится больше процессов — их свяжет `LISTEN/NOTIFY` того же Postgres
  (или Redis).

### Этап 4. Слой знаний и поиск — основа GraphRAG

**Справочники:**
- **продуктов** — `app.products`: название, синонимы, ключи, ОКПД2 / ТН ВЭД /
  CAS (часть уже определяется);
- **преобразований** — `app.transformations`: входы → выходы, источник —
  раздел ИТС или граф.

Узлы графов ссылаются на продукты. Тогда «тот же продукт в другом графе» и
«переувязать узлы» — запрос, а не сравнение строк.

**Готовые рёбра уже есть.** Разбор разделов ИТС пишет «процесс: входы →
выходы» и роли веществ. Это и есть граф знаний из документов — его достаточно
перенести в эти таблицы.

**Векторы (pgvector).**
- Описания разделов и продуктов → эмбеддинги (DashScope text-embedding; на
  180 разделов — копейки).
- Поиск — по словам, по смыслу и по связям графа (сосед, предок,
  альтернатива).

**Права.** Поиск ИИ видит только графы, доступные пользователю (этап 3б), и
общую базу источников.

### Этап 5. Диалог с ИИ

**Поле «Задача для ИИ» на полотне**, например: «добавь альтернативные способы
производства бензола».

Модель работает **инструментами**, а не прямым доступом к базе:
- найти продукт и его источники;
- построить шаг — нашим конвейером (источники → обобщение → разбор со всеми
  страховками);
- показать превью;
- добавить в граф;
- связать с существующим узлом.

Каждое изменение проходит через превью и подтверждение человека, как шаг
сейчас.

**Свои права.** С этапа 3в правки ИИ идут теми же операциями, что и у людей.
Остальные на графе видят «ИИ (по просьбе Анны) добавляет шаг…», а отменить
их можно как обычные.

**Проверка** — сценарии e2e:
- «альтернативы бензола»;
- «довести цепочку от фенола до волокна»;
- на подставных ответах, а живьём — по просьбе владельца.

## Риски и как их закрываем

| Риск | Что делаем |
|---|---|
| Потеря данных при переносе | Файлы не удаляются; пробный прогон; сравнение выгрузок; обратный скрипт |
| Сбой сервера или диска | Ежедневная зашифрованная копия в отдельный репозиторий (`BACKUP.md`); восстановление проверено руками |
| Потеря закрытого ключа копий | Ключ — в двух местах у владельца (менеджер паролей + ещё одно); без него копии не читаются |
| Память сервера (2 ГБ, рядом API и VPN) | Postgres с `shared_buffers=128MB` — около 150–250 МБ; данных мало. Сокеты — по нескольку КБ на подключение |
| Два хранилища расходятся во время перехода | Переключатель — или файлы, или pg, двойной записи нет; перенос в тихое время, библиотека маленькая (минуты) |
| Старые клиенты на сайте | API тот же; версия, токен, сокет — необязательны, пока владелец не включит |
| Чужие запросы к модели за счёт владельца | С этапа 3а — только после входа и с дневным пределом |
| Утечка токенов | Короткий access в памяти; refresh в httpOnly-cookie с поворотом и отзывом цепочки |
| Персональные данные (152-ФЗ) | Согласие, оператор в документах, хранение и копии в РФ с этапа 3а |
| Несколько процессов сервера разделят комнаты | Один процесс pm2; при росте — `LISTEN/NOTIFY` |
