# prompt-check — промпты и разбор шага

Две части: бесплатная (без модели) и с живой моделью (стоит денег).

## 1. Без модели — всегда
```bash
npm test                                                      # разбор шага: test/step-build.test.js
node .claude/skills/prompt-check/scripts/replay.cjs --dry     # промпт обобщения собирается
```
- `npm test` — страховки `build.js` по тексту обобщения на подставных
  ответах разборщика: потерянный выход и второе сырьё возвращаются, побочные
  продукты восстанавливаются и не путаются (вода, «Фенол» ≠ «Бисфенол А»),
  пустое «Что производят» — 422 без вызова модели. Меняешь `build.js` —
  добавь сюда случай.
- `--dry` прогоняет настоящий обработчик `/gpt/step/aggregate` с подменённой
  моделью на каждом кейсе и проверяет собранный промпт: подстановки
  заполнены, данные отделены метками `<lineage>`, `<target_product>`,
  `<existing_chain>`, `<blocks>`.

## 2. Живая модель — по согласованию с владельцем
```bash
node .claude/skills/prompt-check/scripts/replay.cjs --out=<папка для ответов> [кейс…]
```
Каждый кейс — **один запрос к модели** (сейчас кейсов 5, ~50 с вместе).
Запрос идёт на сервер (по умолчанию боевой, `--api=URL` — другой) с
промптами **из этого репозитория** — как из окна «Редактировать промпт» в
клиенте, поэтому проверяется ветка, даже если на сервере старый код.
Ответы сохраняются в `<папка>/<кейс>.md`; перепроверить их без модели (после
правки проверок) — `--answers=<папка>`.

Скрипт повторяет то, что сервер ветки добавляет к модели, даже если боевой
сервер старее:
- **промежуточные продукты раздела** (`intermediates` у источника в
  фикстуре — из базы) ставит строкой в начало блока, как
  `aggregate.js` → `withIntermediates`;
- **дозапрос о перепрыгивании уровня**: если основной шаг вышел мимо
  промежуточных продуктов, названных в его же описании
  (`routes/step/utils/levelSkip.js`), задаёт модели тот же второй вопрос —
  **+1 запрос** на такой кейс; в выводе — строка `↻ дозапрос …`. Проверки
  идут по итоговому ответу, как его отдал бы сервер.

Если сервер уже сам это делает (его промпт по умолчанию знает строку
промежуточных — с `ef8a114`), скрипт ничего не повторяет: шлёт запрос как
клиент, а о дозапросе пишет по полю `levelCheck` ответа сервера.

Проверки каждого ответа (`scripts/checks.cjs`): нет эха входных данных;
шаблон соблюдён (продукт, три поля списком); раскрываемый продукт — первый
вход основного шага и есть во входах альтернатив; новые продукты не ведут в
родословную; в «Контроле шага» посчитаны блоки, основной шаг — с наибольшим
«всего»; плюс ожидания кейса (`expect` в фикстуре).

Модель отвечает не детерминированно. Провал, который не повторяется при
втором прогоне этого кейса, — шум; повторился — регрессия промпта.

## Кейсы
`fixtures/<кейс>.json`: `note` (что проверяет), `expect`, `request` — тело
запроса обобщения, как его шлёт клиент (источники, цепочка, родословная,
провайдер и модель); у источников из базы — `intermediates` (промежуточные
продукты раздела из базы: их сервер ветки берёт сам по `sectionId`).

| Кейс | Что ловит |
|---|---|
| `phenol-down` | перепрыгивание уровня: от фенола — циклогексанон, не капролактам; выбор основного по числу блоков |
| `phenol-down-db` | то же только на разделах базы (без найденного в интернете): в описании раздела вся схема до капролактама; у разделов — промежуточные продукты из базы (строка в начале блока). Живой `phenol-chain` 2026-10-29 проваливал его 2 раза из 2 |
| `phenol-down-prod` | фенол по базе после выкладки: по одному блоку на вариант; не капролактам и не поток («Алкилат»): ложное срабатывание проверки уровня 2026-10-29 |
| `bisphenol-a-down` | поликарбонат среди вариантов (расплавный путь и фосгенный) |
| `diphenyl-carbonate-down` | основной — поликарбонат из ДФК + бисфенола А с побочным фенолом; раньше модель писала описание вместо названия продукта |

`expect` понимает: `forbidOutputs`, `someOutputs`, `mainOutputs`,
`mainInputs`, `mainByproducts` (списки названий; сравнение без уточнений в
скобках и регистра). Новый кейс: возьми тело запроса
`POST /api/graphs/gpt/step/aggregate` (DevTools → Network → Payload в
клиенте) и опиши, что должно получиться.

## Как докладывать
Итог: сколько проверок прошло в `npm test`, `--dry` и (если запускал)
живом прогоне, сколько запросов к модели ушло, провалы — строкой с
подробностью. Ответы модели целиком не пересказывай — дай путь к `.md`.
